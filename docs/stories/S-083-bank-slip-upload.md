## Goal
A buyer with a bank-transfer order can upload a payment slip (image or PDF). The server checks the file, stores it in the private bucket with no public link, records it in `bank_transfer_slips`, and reads the bank details and slip status for the buyer's order page. Buyers can upload again after a rejection.

## Requirements covered
- REQ-154 (CONFIRMED): the buyer picks "Bank transfer", sees the bank details, pays and uploads the slip (image or PDF).
- REQ-154b (ASSUMED): the order waits as `pending_verification`; rejection lets the buyer upload again.
- REQ-055 (CONFIRMED): no permanent public file links.
- Not decided here: REQ-154c (OPEN, Q72): allowed file types and size. They are set from configuration (see Assumptions); changing them is a config change.

## Acceptance criteria
- [ ] AC1: `uploadBankSlip(orderId, formData)` calls `requireActiveAccount()`, accepts only the owner of a `pending_verification` bank-transfer order, and refuses anything else with `not_allowed` or `not_found` (another user's order id returns `not_found`).
- [ ] AC2: The file is validated on the server: the real content type is read from the file bytes (not the extension or the browser's type); only the allowed image types and PDF pass; the size limit comes from configuration; an empty file or a mismatch is refused with `slip_invalid`.
- [ ] AC3: The stored object name is generated by the server (the uploaded name is discarded) and stored in the PRIVATE bucket (S-006) with no public URL. The key is stored in `bank_transfer_slips.file_key` (unique) with `order_id`, `uploaded_by`, `mime_type`, `size_bytes`, status `uploaded`.
- [ ] AC4: Several slips per order are allowed; earlier slips (including rejected ones) are kept; one new upload after a rejection does not delete the old file or row.
- [ ] AC5: Upload attempts are rate limited per order (10 per hour, to confirm); more returns `rate_limited`.
- [ ] AC6: `getBankOrderView(orderId)` (owner only) returns the order number (shown as the payment reference), the bank details read from the setting `bank_account_details` in `site_settings` (never hardcoded), the order status and, per slip, only `status`, `uploaded_at` and the rejection reason, never the file key.
- [ ] AC7: A bank order whose slip was uploaded cannot be cancelled by the buyer (enforced in S-078 `cancelPendingOrder`; asserted here with a slip present).
- [ ] AC8: If the file store write succeeds but the database insert fails (or the reverse), no orphan row or orphan file stays referenced: the upload either fully succeeds or leaves nothing the buyer can see.
- [ ] AC9: Slip contents, names, keys and bank details are never written to logs.
- [ ] AC10: Staff are told a slip is waiting through the admin badge (S-101) only; no email to staff in Release 1.

## Edge cases
- [ ] EC1: A PDF renamed `.jpg`, or a `.jpg` that is really an executable: refused (content check).
- [ ] EC2: A file one byte over the limit: refused; nothing stored.
- [ ] EC3: A suspended buyer or a signed-out request: refused.
- [ ] EC4: Two uploads at once for the same order: both are stored as separate slips; the queue (S-084) shows the newest `uploaded` slip.
- [ ] EC5: The order was cancelled or expired meanwhile: refused with `validation_failed`.
- [ ] EC6: The `bank_account_details` setting is empty: `getBankOrderView` returns the order with an empty details value and the page shows nothing misleading (S-094 handles the wording).
- [ ] EC7: Hosting request-size limit is lower than the slip limit: the Plan records the hosting test result (10 MB through our own server was tested in S-002); the limit never exceeds it.

## Contract
- Server action `uploadBankSlip` and read `getBankOrderView` in `lib/bank/slips.ts`; types `types/bank-slip.ts` (BankSlipStatus, BankOrderView); error code `slip_invalid` added to `types/api.ts`.
- Consumed by: S-084 (admin queue), S-094 (bank transfer screen), S-096 (My Purchases status).

## Out of scope
- Approve, reject, expiry (S-084). Emails (S-088). Slip retention and purge (`purge_old_logs`, later; legal advice Q34).
- WhatsApp slip sending (the owner chose upload, REQ-154; the client confirms in Q72).

## Assumptions accepted
- Allowed types: JPEG, PNG and PDF; maximum size set by a configuration value chosen during plan approval and not above what the hosting test allows. REQ-154c leaves the exact types and size OPEN (Q72); the answer changes only this configuration.
- Slip retention follows the accounting-period decision (commerce 17); nothing is deleted by this story.
- Upload rate limit 10 per hour per order is "to confirm" in commerce 13.
