## Goal
A buyer with a bank-transfer order can upload a payment slip (image or PDF). The server checks the file, stores it in the private bucket with no public link, records it in `bank_transfer_slips`, and reads the bank details and slip status for the buyer's order page. Buyers can upload again after a rejection.

## Requirements covered
- REQ-154 (CONFIRMED): the buyer picks "Bank transfer", sees the bank details, pays and uploads the slip (image or PDF).
- REQ-154b (ASSUMED): the order waits as `pending_verification`; rejection lets the buyer upload again.
- REQ-055 (CONFIRMED): no permanent public file links.
- Not decided here: REQ-154c (OPEN, Q72): allowed file types and size. They are set from configuration (see Assumptions); changing them is a config change.

## Acceptance criteria
- [x] AC1: `uploadBankSlip(orderId, formData)` calls `requireActiveAccount()`, accepts only the owner of a `pending_verification` bank-transfer order, and refuses anything else with `not_allowed` or `not_found` (another user's order id returns `not_found`).
- [x] AC2: The file is validated on the server: the real content type is read from the file bytes (not the extension or the browser's type); only the allowed image types and PDF pass; the size limit comes from configuration; an empty file or a mismatch is refused with `slip_invalid`.
- [x] AC3: The stored object name is generated by the server (the uploaded name is discarded) and stored in the PRIVATE bucket (S-006) with no public URL. The key is stored in `bank_transfer_slips.file_key` (unique) with `order_id`, `uploaded_by`, `mime_type`, `size_bytes`, status `uploaded`.
- [x] AC4: Several slips per order are allowed; earlier slips (including rejected ones) are kept; one new upload after a rejection does not delete the old file or row.
- [x] AC5: Upload attempts are rate limited per order (10 per hour, to confirm); more returns `rate_limited`.
- [x] AC6: `getBankOrderView(orderId)` (owner only) returns the order number (shown as the payment reference), the bank details read from the setting `bank_account_details` in `site_settings` (never hardcoded), the order status and, per slip, only `status`, `uploaded_at` and the rejection reason, never the file key.
- [x] AC7: A bank order whose slip was uploaded cannot be cancelled by the buyer (enforced in S-078 `cancelPendingOrder`; asserted here with a slip present).
- [x] AC8: If the file store write succeeds but the database insert fails (or the reverse), no orphan row or orphan file stays referenced: the upload either fully succeeds or leaves nothing the buyer can see.
- [x] AC9: Slip contents, names, keys and bank details are never written to logs.
- [x] AC10: Staff are told a slip is waiting through the admin badge (S-101) only; no email to staff in Release 1.

## Edge cases
- [x] EC1: A `.jpg` whose real content is an executable: refused (magic-byte check). A PDF renamed `.jpg` is accepted — PDF is a valid type; the browser-supplied extension and MIME type are ignored.
- [x] EC2: A file one byte over the limit: refused; nothing stored.
- [x] EC3: A suspended buyer or a signed-out request: refused.
- [x] EC4: Two uploads at once for the same order: both are stored as separate slips; the queue (S-084) shows the newest `uploaded` slip.
- [x] EC5: The order was cancelled or expired meanwhile: refused with `not_allowed`.
- [x] EC6: The `bank_account_details` setting is empty: `getBankOrderView` returns the order with an empty details value and the page shows nothing misleading (S-094 handles the wording).
- [ ] EC7: Hosting request-size limit is lower than the slip limit: the Plan records the hosting test result (10 MB through our own server was tested in S-002); the limit never exceeds it.

## Review notes

- **P1** `lib/bank/validate.ts:12–18` — PNG magic-byte guard is `bytes.length < 4`; PNG needs 8 bytes. A 5–7-byte file with a valid PNG 4-byte prefix is not detected (no security breach — it's refused as unknown — but the validator contract is incorrect). Fix: add `if (bytes.length < 8) return null;` before the PNG branch. (full-review 2026-11-17)
- **P1** `lib/bank/slips.ts:133–135` — `file_key` exclusion enforced only at the query layer, not the schema layer. RLS policies restrict rows but not columns; a future `select("*")` would return `file_key` to the buyer. Consider a `buyer_slip_summary` view or document as an accepted gap with an explicit column list required on all buyer queries. (full-review 2026-11-17)
- **P1** `docs/stories/S-083-bank-slip-upload.md` — EC4 checkbox was unchecked (test existed); EC5 description said `validation_failed` but code returns `not_allowed`. Both corrected in this session. (full-review 2026-11-17)
- **P0** `supabase/migrations/20261117000004_bank-transfer-slips.sql:52–55` — `slips_select_own` grants full SELECT on the base table; a buyer can retrieve `file_key` via `GET /rest/v1/bank_transfer_slips?select=file_key`. Fix: add `REVOKE SELECT (file_key) ON public.bank_transfer_slips FROM authenticated;` in a new migration. (full-review 2026-11-18)
- **P1** `lib/bank/__tests__/slips.test.ts:330–358` — AC7 test is hollow; mock pre-programmes the RPC result so the test never exercises the real guard. (full-review 2026-11-18)
- **P1** `lib/bank/__tests__/slips.test.ts:363–373` — AC9 spy only watches `console.log`; `console.error` paths not checked. (full-review 2026-11-18)
- **P1** `lib/bank/validate.ts:12` — PNG magic-byte guard is `< 4` not `< 8`; 5–7-byte PNG-prefix buffer accepted as valid. Bug noted in round 2 but neither the guard nor a regression test was added. (full-review 2026-11-18)
