## Goal

Create the empty but runnable Next.js project: strict TypeScript, standalone build, the one configuration module that reads every setting from environment variables and fails at startup with a clear message, the Supabase browser and server clients, and `scripts/check.sh` with Vitest. Every later story builds on this, so it must be small and exact.

## Requirements covered

- REQ-197c (CONFIRMED): login system is Supabase Auth, not Firebase; this story provides the Supabase clients the auth stories use.
- No other REQ id; the rest is infrastructure: no hardcoded configuration (CLAUDE.md), the standalone build (decision X4), the allowed import style and folder layout (file structure design section 3 and rules).

## Acceptance criteria

- [ ] AC1: a Next.js App Router project exists with the Next.js version tested in S-001, TypeScript strict, npm, the Node version confirmed by S-001 D1 (recorded in `package.json` `engines` and `.nvmrc`), the `@/*` path alias, and `next.config.ts` with `output: "standalone"`.
- [ ] AC2: `lib/config.ts` reads every setting from `process.env`, validates it with a schema, and exposes two objects: `publicConfig` (values safe for the browser, from `NEXT_PUBLIC_*`) and `serverConfig` (secrets). In this story the required settings are the Supabase project URL, the Supabase anon key, the Supabase service-role key and `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`. Later stories add their own settings to the same module.
- [ ] AC3: if a required setting is missing, empty (including whitespace only) or invalid (for example the URL is not a URL), the server refuses to start with one clear error that lists the setting names (never the values). This is done from `instrumentation.ts` calling the loader at server start.
- [ ] AC4: `serverConfig` cannot be read in the browser: accessing it when `window` exists throws, and `lib/supabase/server.ts` starts with `import "server-only"`. No secret is read through a `NEXT_PUBLIC_*` name.
- [ ] AC5: `lib/supabase/client.ts` (browser, anon key) and `lib/supabase/server.ts` (server: a cookie-based client for server components and actions, and one function that returns the service-role client) exist, take every value from `lib/config.ts`, and read the session only when a caller asks for it (nothing in a layout reads the session; public pages must not run auth).
- [ ] AC6: `.env.example` lists variable names only (no values, no secrets). `.gitignore` excludes `.env*` except `.env.example` and keeps `.claude/settings.local.json` out.
- [ ] AC7: `scripts/check.sh` runs lint, type check and the Vitest unit tests in that order and exits non-zero when any step fails. Vitest is installed with one config and the tests for AC2 to AC4.
- [ ] AC8: `next build` succeeds and the standalone output starts with `node server.js` when the required settings are present, and fails with the AC3 message when one is removed.

## Edge cases

- [ ] EC1: a setting is present but only whitespace. Treated as missing.
- [ ] EC2: the error message must not contain any secret value, even for an invalid value.
- [ ] EC3: `NEXT_PUBLIC_*` values are fixed at build time (infrastructure design 5.1). The build fails if a `NEXT_PUBLIC_*` value is missing at build; staging and production are separate builds.
- [ ] EC4: `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` differs between processes on Path A. The config only checks it is present and has the expected length; making it identical across processes is a deploy rule (infrastructure design 10).
- [ ] EC5: a client component imports `lib/supabase/server.ts` by mistake. The build fails because of `server-only`.
- [ ] EC6: the local development stack uses local Supabase values; the same loader accepts them.
